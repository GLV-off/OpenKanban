# AGENTS — правила проекта Open Kanban

## Что это

Open Kanban — открытая self-hosted реализация сервиса и веб-клиента для
управления задачами в стиле Kanban: рабочие пространства, доски, колонки,
задачи, роли пользователей. Бекенд — Rust + SQLite, клиент — TypeScript + React.

Документация — единственный источник согласованных решений. Код, расходящийся
с `doc/`, считается ошибкой (либо код, либо документ).

## Структура репозитория

```
backend/open_kanban_service/   # Rust-бинарь HTTP API (Cargo workspace member)
frontend/open_kanban_web/      # Vite + React SPA (появится в итерации 0)
doc/                           # документация проекта (русский язык)
tools/                         # скрипты: генерация API-типов, smoke, dev
```

- Rust-крейты добавляются только при реальной необходимости; преждевременное
  дробление на `core`/`api`/`infra` запрещено (YAGNI).
- Доменные модули не зависят от типов `axum`; HTTP-слой маппит DTO ↔ домен.
- Сгенерированные артефакты (типы API, OpenAPI) коммитятся, чтобы сборка не
  требовала запущенного сервиса.

## Команды

Бекенд (из корня репозитория):

```bash
cargo run -p open_kanban_service     # запуск сервиса
cargo test                           # все тесты workspace
cargo fmt --check                    # форматирование
cargo clippy --all-targets -- -D warnings
```

Фронтенд (из `frontend/open_kanban_web`, появится в итерации 0):

```bash
npm ci
npm run dev
npm run build
npm run test        # vitest run
npx biome ci .
```

Конфигурация сервиса — только через переменные окружения; значения по
умолчанию годятся для локального запуска. Секреты в репозиторий не попадают.

## Правила кода

- Rust edition 2024 (нужен rustc ≥ 1.85; ориентир — текущий стабильный,
  проверено на 1.96); форматирование `rustfmt`, линт `clippy` без предупреждений.
- Ошибки: типизированные (`thiserror`), маппинг в `problem+json` (RFC 9457) в
  одном месте. `unwrap`/`expect` — только в тестах и при доказанной
  невозможности ошибки.
- Миграции БД: только вперёд, файлами `migrations/NNNN_*.sql`; применённые
  миграции не редактируются.
- Все изменения данных о задачах — в транзакции; инварианты из
  [doc/domain_ru.md](doc/domain_ru.md) обязательны к соблюдению.
- Права проверяются на каждом эндпоинте; на каждый запрет — негативный тест.
- API-контракт: `/api/v1`, JSON, id строками, время RFC 3339 UTC, ошибки
  `application/problem+json`.
- Пароли — только argon2id; refresh-токены — только хешем; секреты и PII не
  логируются.
- Фронтенд: строгий TypeScript, типы API из OpenAPI, серверное состояние —
  TanStack Query; бизнес-правила не дублируются на клиенте.
- Язык интерфейса I1 — русский; тексты выносятся в словарь.

## Правила документации

- Документы в `doc/` — на русском, с явными пометками **ПРИНЯТО**,
  **ПРЕДЛОЖЕНИЕ**, **ОТКРЫТО**.
- Изменение контракта, схемы БД, прав или стека требует обновления
  соответствующего документа в том же изменении.
- Открытые вопросы фиксируются в
  [doc/domain_ru.md](doc/domain_ru.md#9-решения-требующие-подтверждения);
  нерешённое решение не «зашивается» в код молча.

## Git

Формат сообщений — Conventional Commits: `feat:`, `fix:`, `docs:`, `refactor:`,
`test:`, `chore:`, `build:`. Исторические коммиты (`NEW:`, `FEAT(...)`) не
переписываются; новые — по правилу выше.

Один коммит — одна логическая причина изменения. Документация и код, которые
относятся к одному решению, — в одном коммите.

## Definition of Done

- Тесты/проверки зелёные; для нового поведения есть проверка (тест или
  демо-сценарий).
- Обновлены README/`doc/`, если изменились запуск, контракт, схема или права.
- Нет секретов, отладочного мусора и закомментированного кода.
- Изменение можно откатить без ручной правки БД.
