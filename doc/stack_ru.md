## 1. Принципы выбора

1. **Стабильность важнее новизны.** Предпочтение — решение с длинной историей
   релизов и предсказуемой политикой ломающих изменений.
2. **Минимум движущихся частей для self-hosted.** Один сервис, файловая БД,
   без обязательных внешних зависимостей (Redis, брокеров, object storage).
3. **Контракт важнее реализации.** OpenAPI-спецификация — источник истины,
   клиентские типы генерируются, а не пишутся руками.
4. **Проверяемость.** Любой выбор должен позволять писать быстрые
   интеграционные тесты без внешней инфраструктуры.
5. **Обратимость.** Решения, которые дорого менять (модель БД, формат `id`),
   фиксируются документом; дешёвые (UI-библиотека, линтер) — меняются свободно.
6. **Один способ делать одно и то же.** Один ID-механизм, один способ
   миграций, один HTTP-клиент на фронте.

### 2.2 Ключевые доводы

- **`axum` 0.8** — не 1.0, но API стабилизировался с 0.6/0.7, релизы редкие и
  осмысленные, экосистема `tower` совместима. Риск ломающих изменений
  компенсируется точным пином минорной версии и осознанным апгрейдом.
- **`sqlx` 0.9** — асинхронность без отдельного пула блокирующих потоков,
  миграции и `query!`-проверки. SQLite-драйвер поддерживает нужные настройки
  (`journal_mode`, `busy_timeout`, `foreign_keys`).
  Важно: `query!` требует либо живой БД, либо офлайн-кэш `.sqlx` в репозитории —
  это часть CI, а не «магия».
- **`utoipa` 6 + `utoipa-axum` 0.3** — единственная зрелая связка
  «derive → OpenAPI» под axum. Совместимость минорных версий нужно проверить
  на первом же эндпоинте; запасной вариант — держать `openapi.yaml` руками
  и валидировать его в CI (контракт важнее способа генерации).

### 2.3 SQLite: настройки и границы

Обязательные параметры подключения:

```text
journal_mode = WAL
foreign_keys = ON
busy_timeout = 5000 ms
synchronous  = NORMAL
```

- Пул: несколько соединений на чтение, запись сериализуется SQLite; при
  `SQLITE_BUSY` — повтор с backoff на уровне слоя доступа к данным.
- Миграции — только вперёд, через `sqlx::migrate!` при старте (или отдельной
  командой в CI/деплое — решается в I0).
- Бэкап: `VACUUM INTO 'backup.db'` или копирование файла после
  `wal_checkpoint(TRUNCATE)`; описывается в README.
- Ограничения, которые принимаем осознанно: один писатель, нет сетевого
  доступа к БД, нет `JSONB`-индексов и полнотекста «из коробки» (FTS5 есть,
  но не в I1).
- **Когда уходить на PostgreSQL:** несколько экземпляров сервиса, устойчивая
  потребность в конкурентной записи, полнотекстовый поиск, аналитика. Слой
  доступа к данным изолируется, чтобы миграция была локальной.

### 3.2 Ключевые доводы

- SPA без SSR: Kanban — интерактивное приложение за авторизацией, SSR не даёт
  выигрыша, но добавляет сервер и усложняет деплой (self-hosted, один бинарь).
- `@tanstack/react-query` снимает 80% боли синхронизации состояния доски с
  сервером; оптимистичное перетаскивание + откат по `onError` — прямое
  попадание в требование TSK-6/UI-2.
- Типы API генерируются из OpenAPI: расхождение контракта и клиента ловится
  сборкой, а не в проде.
- `dnd-kit` выбран за доступность (клавиатура, скринридеры) и поддержку
  сенсоров; альтернатива Atlassian рассматривается как запасная — обе
  библиотеки активны, риск низкий.

## 4. Контракт и взаимодействие

- Спецификация: OpenAPI 3.1, генерируется из маршрутов/типов бекенда,
  доступна по `/api/v1/openapi.json`; Swagger UI — по `/api/v1/docs` в dev.
- Генерация клиентских типов: `openapi-typescript` в `tools/` или npm-скрипт
  фронтенда; результат коммитится, чтобы сборка не зависела от запущенного
  бекенда.
- Ошибки: `application/problem+json` (RFC 9457):

```json
{
  "type": "https://openkanban.local/problems/conflict",
  "title": "Task was modified",
  "status": 409,
  "code": "TASK_VERSION_CONFLICT",
  "detail": "Expected version 4, actual 5",
  "instance": "/api/v1/tasks/0190f3c2-..."
}
```

- Время — RFC 3339 UTC; `id` — строки; списки — `{ items, next_cursor }`
  (пагинация вводится в I2, формат фиксируется заранее).
- Авторизация: `Authorization: Bearer <access>`; refresh — httpOnly cookie
  `ok_refresh` (`SameSite=Strict`, `Secure` при HTTPS, `Path=/api/v1/auth`).
  CSRF для cookie-эндпоинта — проверка `Origin` + double-submit при
  необходимости (решение фиксируется в I1 вместе с тестами).

## 5. Структура репозитория

```
open_kanban/
├─ Cargo.toml                 # виртуальный workspace
├─ backend/
│  └─ open_kanban_service/    # бинарь сервиса
│     ├─ src/
│     │  ├─ main.rs           # запуск, конфиг, роутер
│     │  ├─ config.rs
│     │  ├─ error.rs
│     │  ├─ auth/             # регистрация, вход, сессии, middleware
│     │  ├─ workspace/        # пространства, участники, роли
│     │  ├─ board/            # доски, колонки, порядок
│     │  ├─ task/             # задачи, перенос, версии
│     │  └─ db/               # пул, транзакции, репозитории
│     └─ migrations/          # SQL-миграции sqlx
├─ frontend/
│  └─ open_kanban_web/        # Vite + React SPA
│     ├─ src/{app,pages,widgets,features,entities,shared}
│     └─ src/shared/api/      # сгенерированные типы + openapi-fetch
├─ doc/                       # документация (рус.)
└─ tools/                     # скрипты: gen-api, smoke, dev
```

Правила: доменные модули бекенда не зависят от `axum`-типов; HTTP-слой
маппит DTO ↔ домен; фронтенд не содержит бизнес-правил, только представление
и оптимистичные подсказки.

## 6. Тесты и качество

| Уровень | Инструмент | Что покрывает |
|---|---|---|
| Домен (backend) | `cargo test` | инварианты: роли, позиции, переходы |
| API (backend) | `cargo test` + `tower::ServiceExt::oneshot` + временная SQLite | коды ответов, права, конфликты `409`, валидация |
| Контракт | проверка `openapi.json` в CI | спецификация валидна и генерируется |
| Фронтенд | `vitest` + Testing Library | компоненты, хуки, откат оптимистичных обновлений |
| E2E | Playwright | сквозной сценарий I1 (UI + API) |
| Качество | `cargo fmt --check`, `cargo clippy -- -D warnings`, `biome ci` | стиль и типовые ошибки |

CI — обязательный шаг перед merge; конкретная площадка (GitHub Actions,
локальный runner) выбирается при настройке I0. Кэш `cargo`/`npm` — обязателен.

## 7. Политика зависимостей

1. Версии фиксируются: `Cargo.lock` и `package-lock.json` коммитятся.
2. Обновление — отдельной задачей, с прогоном тестов; не «заодно с фичей».
3. `0.x`-зависимости (`axum`, `sqlx`, `utoipa`, `tower-http`) обновляются
   осознанно: читаем changelog, проверяем совместимость.
4. Новая зависимость добавляется, если: решает задачу, которую иначе писать
   > 200 строк, поддерживается, лицензия совместима, есть альтернатива
   (не вендор-лок).
5. `cargo deny` (лицензии, уязвимости) — опционально в I0, обязательно до
   первого публичного релиза.
