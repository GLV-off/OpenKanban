Документ фиксирует **что** моделируем. **Как** это ложится на SQLite и API —
в [stack_ru.md](stack_ru.md). Пометки: **ПРИНЯТО** — из брифа,
**ПРЕДЛОЖЕНИЕ** — рекомендация, **ОТКРЫТО** — не решено.

## 1. Глоссарий

| Термин | Значение |
|---|---|
| Пользователь (User) | Аккаунт с email и паролем. Существует независимо от пространств |
| Рабочее пространство (Workspace) | Контейнер верхнего уровня: участники, роли, доски. Один владелец |
| Участник (Membership) | Связь пользователя с пространством и его роль в нём |
| Доска (Board) | Kanban-доска внутри пространства; содержит колонки |
| Колонка (Column) | Стадия/список на доске; содержит задачи с порядком |
| Задача (Task) | Единица работы: `id`, заголовок, описание; находится в колонке доски |
| Позиция (Position) | Порядковый номер задачи в колонке / колонки на доске / доски в пространстве |
| Перенос (Transfer) | Смена доски и/или колонки задачи; `id` задачи сохраняется |
| Владелец (Owner) | Роль с полными правами на пространство; ровно одна на пространство |
| Администратор (Admin) | Роль, назначаемая владельцем: управление участниками и досками |
| Участник (Member) | Обычный пользователь пространства: работа с задачами |

## 2. Обзор модели

```
User ──1──* Membership *──1── Workspace ──1──* Board ──1──* Column ──1──* Task
                                │ owner_id                                    │
                                └─────────────── User                          │
                                                                               │
Task.board_id ─────────────────────────────────────────────────────────────────┘
Task.column_id ──(column belongs to board)
```

- `Task` не существует вне `Column`/`Board`.
- `Board` не существует вне `Workspace`.
- `Membership` — единственный источник прав внутри пространства.
- Глобальной роли «администратор сервиса» в I1 нет: администрирование —
  только внутри пространства.

## 3. Сущности и поля

Имена таблиц и полей — предложение; в коде допустимы иные, но смысл и
ограничения должны сохраняться.

### 3.1 `users`

| Поле | Тип | Ограничения |
|---|---|---|
| `id` | UUIDv7 | PK |
| `email` | TEXT | NOT NULL, UNIQUE, хранится нормализованным (`trim` + нижний регистр) |
| `password_hash` | TEXT | NOT NULL, PHC-строка argon2id |
| `display_name` | TEXT | NOT NULL, 1..80 |
| `email_verified` | BOOLEAN | NOT NULL DEFAULT false (в I1 не используется, но поле есть) |
| `status` | TEXT | `active` \| `disabled`, DEFAULT `active` |
| `created_at` | TEXT (RFC 3339 UTC) | NOT NULL |
| `updated_at` | TEXT (RFC 3339 UTC) | NOT NULL |

### 3.2 `sessions` (refresh-сессии)

| Поле | Тип | Ограничения |
|---|---|---|
| `id` | UUIDv7 | PK |
| `user_id` | UUID | FK → `users.id`, ON DELETE CASCADE |
| `token_hash` | TEXT | NOT NULL, UNIQUE, SHA-256 от refresh-токена |
| `issued_at` / `expires_at` | TEXT | NOT NULL |
| `revoked_at` | TEXT | NULL |
| `replaced_by` | UUID | NULL, FK → `sessions.id` (ротация) |
| `user_agent` | TEXT | NULL, обрезается по длине |

### 3.3 `workspaces`

| Поле | Тип | Ограничения |
|---|---|---|
| `id` | UUIDv7 | PK |
| `name` | TEXT | NOT NULL, 1..80 |
| `owner_id` | UUID | NOT NULL, FK → `users.id` |
| `created_at` / `updated_at` | TEXT | NOT NULL |
| `archived_at` | TEXT | NULL |

Владелец дублируется в `owner_id` (быстрый доступ) и в `memberships`
(единый источник прав). Согласованность обеспечивается транзакцией.

### 3.4 `memberships`

| Поле | Тип | Ограничения |
|---|---|---|
| `workspace_id` | UUID | FK → `workspaces.id`, ON DELETE CASCADE |
| `user_id` | UUID | FK → `users.id`, ON DELETE CASCADE |
| `role` | TEXT | `owner` \| `admin` \| `member` |
| `created_at` | TEXT | NOT NULL |
| `invited_by` | UUID | NULL, FK → `users.id` |

PK `(workspace_id, user_id)`. Частичный уникальный индекс
`UNIQUE(workspace_id) WHERE role = 'owner'` — гарантия одного владельца.

### 3.5 `boards`

| Поле | Тип | Ограничения |
|---|---|---|
| `id` | UUIDv7 | PK |
| `workspace_id` | UUID | NOT NULL, FK → `workspaces.id`, ON DELETE CASCADE |
| `title` | TEXT | NOT NULL, 1..120 |
| `description` | TEXT | NULL, до 4000 символов |
| `position` | INTEGER | NOT NULL, порядок среди досок |
| `created_by` | UUID | FK → `users.id` |
| `created_at` / `updated_at` | TEXT | NOT NULL |
| `archived_at` | TEXT | NULL |

### 3.6 `columns`

| Поле | Тип | Ограничения |
|---|---|---|
| `id` | UUIDv7 | PK |
| `board_id` | UUID | NOT NULL, FK → `boards.id`, ON DELETE CASCADE |
| `title` | TEXT | NOT NULL, 1..80 |
| `position` | INTEGER | NOT NULL |
| `wip_limit` | INTEGER | NULL — задел на будущее, в I1 не используется |
| `created_at` / `updated_at` | TEXT | NOT NULL |

Дополнительно `UNIQUE(id, board_id)` — опора для составного FK из `tasks`.

### 3.7 `tasks`

| Поле | Тип | Ограничения |
|---|---|---|
| `id` | UUIDv7 | PK, глобальный, не меняется при переносе |
| `board_id` | UUID | NOT NULL |
| `column_id` | UUID | NOT NULL |
| `title` | TEXT | NOT NULL, 1..200 |
| `description` | TEXT | NULL, до 20000 символов, Markdown |
| `position` | INTEGER | NOT NULL, порядок в колонке |
| `version` | INTEGER | NOT NULL DEFAULT 0, оптимистичная блокировка |
| `created_by` / `updated_by` | UUID | FK → `users.id` |
| `created_at` / `updated_at` | TEXT | NOT NULL |
| `archived_at` | TEXT | NULL |

Составной FK `(column_id, board_id)` → `columns(id, board_id)` делает
невозможным состояние «задача ссылается на колонку чужой доски» на уровне БД.
Индекс `(board_id, column_id, position)` — для выборки доски.

### 3.8 `activity` (I2)

| Поле | Тип | Ограничения |
|---|---|---|
| `id` | UUIDv7 | PK |
| `workspace_id` | UUID | NOT NULL, FK → `workspaces.id` |
| `actor_id` | UUID | FK → `users.id` |
| `entity_type` | TEXT | `task` \| `board` \| `column` \| `membership` |
| `entity_id` | UUID | NOT NULL |
| `action` | TEXT | `created` \| `updated` \| `moved` \| `archived` \| ... |
| `payload` | TEXT (JSON) | Детали: `from_board_id`, `to_board_id`, `from_column_id`, `to_column_id` |
| `created_at` | TEXT | NOT NULL |

## 4. Инварианты

Правила, которые обязаны выполняться всегда. Часть обеспечивается схемой БД,
часть — транзакциями и доменным слоем.

| ID | Инвариант | Как обеспечивается |
|---|---|---|
| I-1 | Email уникален без учёта регистра | нормализация в приложении + `UNIQUE` |
| I-2 | У пространства ровно один владелец | `owner_id` NOT NULL + частичный уникальный индекс по `memberships` |
| I-3 | Владелец всегда имеет membership с ролью `owner`; смена владельца — одна транзакция | доменный сервис + тест |
| I-4 | Владелец не может быть исключён или понижен без передачи владения | проверка в сервисе |
| I-5 | Роли упорядочены: `owner > admin > member`; назначать `admin` может только владелец | проверка прав |
| I-6 | `board.workspace_id` существует; `column.board_id` существует | FK |
| I-7 | Колонка задачи принадлежит доске задачи | составной FK `(column_id, board_id)` |
| I-8 | Задача не может ссылаться на доску другого пространства | следствие I-6, I-7 |
| I-9 | Порядок детерминирован: `ORDER BY position, id` | позиции + сортировка по `id` как тай-брейк |
| I-10 | Перенос задачи атомарен: либо изменены и `board_id`, и `column_id`, и `position`, либо ничего | одна транзакция |
| I-11 | `task.version` увеличивается при каждом изменении; клиент присылает ожидаемую версию | `UPDATE ... WHERE id = ? AND version = ?`; `0` строк → `409` |
| I-12 | Архивные задачи по умолчанию не попадают в списки | фильтр `archived_at IS NULL` |
| I-13 | Чужие ресурсы не раскрываются: обращение к пространству без членства → `404`, не `403` | проверка доступа до загрузки сущности |
| I-14 | Пароль, хеш пароля и refresh-токен не попадают в ответы и логи | DTO без полей + запрет `Debug` |

## 5. Роли и права

Матрица для I1. «—» — запрещено, «+» — разрешено, «±» — ограничение в скобках.

| Действие | owner | admin | member |
|---|---|---|---|
| Видеть пространство и его доски | + | + | + |
| Изменять название/описание пространства | + | + | — |
| Архивировать/удалять пространство | + | — | — |
| Передавать владение | + | — | — |
| Добавлять участника (role `member`) | + | + | — |
| Назначать/снимать `admin` | + | — | — |
| Исключать участника (`member`) | + | + | — |
| Исключать `admin` | + | — | — |
| Выходить из пространства | ± (только передав владение) | + | + |
| Создавать доску | + | + | — (см. Q3) |
| Изменять/архивировать доску | + | + | — (см. Q3) |
| Создавать/менять/удалять колонки | + | + | — |
| Создавать задачу | + | + | + |
| Редактировать задачу | + | + | + |
| Перемещать задачу внутри доски | + | + | + |
| Переносить задачу на другую доску | + | + | + |
| Архивировать/удалять задачу | + | + | + |
| Видеть список участников пространства | + | + | + |
| Искать пользователя по точному email (для добавления) | + | + | — |

Правила проверяются на каждом эндпоинте; матрица покрывается интеграционными
тестами (в том числе негативными).

## 6. Ключевые процессы

### 6.1 Регистрация и вход

1. `POST /api/v1/auth/register` — email нормализуется, проверяется политика
   пароля, сохраняется argon2id-хеш. Ответ: пользователь без хеша.
2. `POST /api/v1/auth/login` — проверка пароля; создаётся `sessions` с
   хешем refresh-токена; клиент получает access-токен и refresh-cookie.
3. `POST /api/v1/auth/refresh` — refresh-токен проверяется по хешу, старый
   помечается `revoked_at` и `replaced_by`, выдаётся новая пара (ротация).
4. `POST /api/v1/auth/logout` — текущая сессия отзывается.

Ограничения: одинаковый ответ на «неверный email» и «неверный пароль»;
задержка/лимит попыток на login; refresh-токен одноразовый (повторное
использование = отзыв цепочки).

### 6.2 Добавление участника (I1)

1. Владелец/админ ищет пользователя по точному email.
2. Если пользователь существует — создаётся `membership(role='member')` в
   одной транзакции.
3. Если не существует — `404` (в I1 приглашения по email не реализуются).
4. Повторное добавление — идемпотентно (`200`/`204`), роль не понижается.

### 6.3 Перенос задачи

Единая операция домена: «переместить задачу в (board, column, position)».

1. Проверка доступа к пространству и обеим доскам (источник/цель).
2. Проверка `version` (оптимистичная блокировка) → иначе `409`.
3. В одной транзакции: обновить `board_id`, `column_id`, `position`,
   `version = version + 1`, `updated_at`, `updated_by`;
   при необходимости — пересчитать позиции в колонке-источнике и
   колонке-цели.
4. Записать событие `moved` в `activity` (I2).
5. Вернуть обновлённую задачу с новым `version`.

Ограничения: `id`, `title`, `description`, `created_at` не меняются;
перенос между пространствами запрещён (Q4); позиция в целевой колонке
вычисляется сервером, клиент передаёт «до/после какой задачи» либо целевой
индекс.

### 6.4 Конкурентные изменения

- Задача: `If-Match` с `version` (или поле `version` в теле) → `409
  Conflict` с актуальным состоянием в теле ответа.
- Перестановка колонок/досок: та же схема для досок (поле `version`
  добавляется при необходимости; в I1 достаточно для задач).
- Фронтенд: оптимистичное обновление, при `409` — откат и сообщение
  «доска изменилась, обновите».

## 7. Идентификаторы и упорядочивание

### 7.1 `id`

**ПРЕДЛОЖЕНИЕ:** UUIDv7 (RFC 9562) для всех сущностей, в API — строка
канонического вида `0190f3c2-...`.

Почему: генерируется клиентом/сервером без координации, монотонен по времени
(хорош для индексов и сортировки), стандартизован, поддержан крейтом `uuid`
(фича `v7`). Это один механизм на весь проект.

Отклонено: ULID (своя кодировка, отдельный крейт, выигрыш незначителен);
автоинкремент (утечка объёма данных, конфликты при переносе между
инсталляциями); «человеческий» ключ как PK (счётчик на пространство —
отдельная фича, см. TSK-9).

### 7.2 Порядок

**ПРЕДЛОЖЕНИЕ:** целочисленная `position` с шагом 1024.

- Вставка в конец: `max(position) + 1024`.
- Вставка между A и B: `A.position + (B.position - A.position) / 2`.
- Если зазор ≤ 1 — перебалансировка колонки (перенумерация 1024, 2048, …)
  в той же транзакции.
- Сортировка всегда `ORDER BY position, id` — детерминизм при совпадении.

Альтернативы (дробные числа, LexoRank-строки) отклонены в I1: SQLite не даёт
точных дробей без потерь, а строковые ранги усложняют код без выигрыша при
наших объёмах.

## 8. Что модель сознательно не содержит

- Отдельной сущности «проект» между пространством и доской.
- Глобальных ролей сервиса и «супер-администратора» (Q-сервисное
  администрирование — вне I1).
- Связи «задача ↔ несколько досок»: задача всегда ровно на одной доске; перенос
  — это смена владельца, а не копия.
- Хранения позиции задачи вне колонки: `position` имеет смысл только вместе с
  `column_id`.
