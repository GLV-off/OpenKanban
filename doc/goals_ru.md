Легенда статусов требований:

- **ПРИНЯТО** — следует из брифа заказчика (обязательно к реализации).
- **ПРЕДЛОЖЕНИЕ** — рекомендация команды, требует подтверждения.
- **ОТКРЫТО** — не решено, вынесено в раздел «Открытые вопросы».

## 1. Видение

Open Kanban — открытая self-hosted реализация сервиса и веб-клиента для
самодостаточного управления задачами в стиле Kanban: рабочее пространство,
доски, колонки, задачи и базовый набор пользователей. Проект не зависит от
внешних SaaS, разворачивается одним сервисом с файловой БД SQLite и
предоставляет открытый HTTP-контракт (OpenAPI), по которому может быть
написан любой клиент, не только наш.

Ключевая идея: **задача — самостоятельная сущность с глобальным
идентификатором**, которая может перемещаться между колонками и досками без
потери истории, а **доступ и роли** определяются членством в рабочем
пространстве.

## 2. Проблема и аудитория

| Аудитория | Проблема | Что даёт Open Kanban |
|---|---|---|
| Небольшая команда (2–20 чел.) | Trello/Jira/YouTrack — внешний SaaS, вендор-лок, лимиты | Свой сервер, свои данные, простой API |
| Разработчик / инди | Нужен минимальный Kanban без подписки | Один бинарь + SQLite, docker/локальный запуск |
| Интегратор | Нужен предсказуемый API для своих инструментов | OpenAPI 3.1 как контракт, версионирование `/api/v1` |

Не целевая аудитория первой итерации: крупные организации с SSO/LDAP,
регуляторными требованиями и тысячами пользователей.

## 3. Целевые сценарии (I1)

1. Пользователь регистрируется по email и паролю, входит в систему.
2. Создаёт рабочее пространство и становится его владельцем.
3. Владелец добавляет участников и назначает администраторов.
4. Администратор создаёт доску и колонки, участники создают задачи.
5. Все участники пространства видят доску, перетаскивают задачи между
   колонками.
6. Задачу можно перенести на другую доску того же пространства — задача
   сохраняет свой идентификатор и содержимое.
7. Владелец управляет пространством; администратор — досками и участниками;
   обычный участник — задачами; чужие пространства недоступны.
8. Обычный участник видит только тех пользователей, с которыми состоит в общих
   пространствах (нет глобального каталога пользователей).

## 4. Цели проекта

| ID | Цель | Измеримый результат |
|---|---|---|
| G1 | Реализовать Kanban-ядро: пространство → доски → колонки → задачи | Сценарии раздела 3 проходят из UI и через API |
| G2 | Сделать перенос задач полноценной операцией домена | Задача перемещается между колонками и досками с сохранением `id`; операция атомарна; история перемещений фиксируется (I2) |
| G3 | Реализовать базовую модель доступа | Один владелец на пространство; роли `owner/admin/member`; проверка прав на каждом эндпоинте; автотесты на запреты |
| G4 | Дать открытый и стабильный контракт | OpenAPI 3.1 покрывает 100% публичных эндпоинтов; клиентские типы генерируются из него; `/api/v1` |
| G5 | Обеспечить самодостаточное развёртывание | Один бинарь + файл SQLite; конфигурация через переменные окружения; миграции применяются при старте |
| G6 | Заложить основу для роста без переписывания | Модульный монолит с явными границами модулей; доступ к данным изолирован в модуле `db` (без преждевременных трейт-абстракций); путь миграции на PostgreSQL описан |
| G7 | Держать проект открытым и понятным | Русскоязычная документация в `doc/`, README с быстрым стартом, воспроизводимая сборка, CI |

## 5. Границы

### 5.1 Входит в первую итерацию (I1)

- Аутентификация: регистрация, вход, обновление сессии, выход.
- Рабочие пространства: создание, просмотр, переименование; владелец.
- Участники: добавление существующего пользователя по email, роли
  `owner/admin/member`, назначение администратора владельцем, исключение и
  самостоятельный выход.
- Доски: создание, переименование, список; колонки с порядком; задачи с
  заголовком, описанием и порядком.
- Перемещение задач: между колонками одной доски и между досками одного
  пространства, включая порядок внутри колонки.
- Видимость пользователей в пределах общих пространств.
- Веб-клиент: вход, выбор пространства, доска с drag & drop, CRUD задач.

### 5.2 Не входит (сознательно)

| Область | Причина / когда вернуться |
|---|---|
| Комментарии, чек-листы, вложения, теги, подзадачи | I3, после стабилизации ядра |
| Realtime-обновления (WebSocket/SSE) | I3; в I1 достаточно обновления по запросу |
| Приватные доски и тонкие права на доску | Решение по видимости ещё не принято (см. открытые вопросы) |
| Приглашения по email и подтверждение email (SMTP) | I2, нужен почтовый транспорт |
| Восстановление пароля | I2 (зависит от SMTP) |
| Несколько рабочих пространств на одну доску, перенос между пространствами | Запрещено в I1; копирование — отдельное решение |
| SSO, OAuth-провайдеры, LDAP | Не входит в обозримый план |
| Мобильные приложения, офлайн-режим | Не входит; API для них уже будет |
| Биллинг, мультитенантность как SaaS | Проект self-hosted |
| Полная локализация | I1 — русский UI; строки выносятся в словарь, EN — позже |
| Публичный API-каталог пользователей / поиск людей по всей базе | Противоречит требованию области видимости |

## 8. Критерии приёмки итерации 1

Итерация считается завершённой, когда на чистой БД воспроизводится сквозной
сценарий:

1. Регистрация пользователя A, создание пространства `W`, A — владелец.
2. Регистрация B и C; A добавляет B участником, B назначается
   администратором, C — участником.
3. B создаёт доску `D1` с колонками «Todo / Doing / Done».
4. A создаёт задачу в «Todo», перетаскивает её в «Doing», порядок сохраняется
   после перезагрузки страницы.
5. B создаёт доску `D2`; C переносит задачу `T` с `D1` на `D2`; `T.id`,
   заголовок и описание не изменились.
6. C не видит пространство `W2`, в котором не состоит: API отвечает `404`.
7. C не может создавать доски, назначать администраторов и исключать
   участников: API отвечает `403`.
8. Два одновременных переноса одной задачи: один успешен, второй получает
   `409`, данные не теряются.
9. Выход и повторный вход работают; refresh-токен отозван после выхода.
10. `cargo test`, `cargo clippy -- -D warnings`, `cargo fmt --check` и тесты
    фронтенда зелёные; OpenAPI-спецификация валидна и покрывает все
    публичные эндпоинты.
