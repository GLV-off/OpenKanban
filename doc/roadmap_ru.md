Принцип: каждая итерация заканчивается **демонстрируемым сценарием** и
зелёными проверками. Никаких «полуготовых» слоёв, которые нельзя запустить.

Гейты (решения до начала работ):

- **G-1**: подтверждены Q1–Q4 из [domain_ru.md](domain_ru.md#9-решения-требующие-подтверждения)
  — до первой миграции схемы БД.
- **G-2**: подтверждены способ передачи токенов (Q7) и видимость профиля
  (VIS-5) — до реализации `auth`.
- **G-3**: выбран способ генерации OpenAPI (utoipa либо ручной `openapi.yaml`)
  — до первого публичного эндпоинта.

## Итерация 0 — Каркас

**Цель:** репозиторий собирается, запускается и проверяется одной командой;
документация и правила согласованы.

Задачи:

1. Починить workspace-манифест (виртуальный манифест, общие поля пакетов).
2. `AGENTS.md`: правила проекта, команды сборки/тестов, карта документации.
3. README: что это, быстрый старт, ссылки на `doc/`.
4. Бекенд: конфигурация из env, `tracing`, `/healthz`, `/readyz`, каркас
   ошибок (`problem+json`), пул SQLite с обязательными PRAGMA, механизм
   миграций.
5. Первая миграция: только `users` + `sessions` (минимум, проверяющий схему).
6. Бекенд: `cargo fmt`, `clippy -D warnings`, тест-заготовка для `/healthz`.
7. Фронтенд: Vite + React + TypeScript, строгий `tsconfig`, роутер, пустая
   страница `Health` и страница логина-заглушки, Biome.
8. `tools/`: команда генерации типов из OpenAPI (пока на заглушке),
   smoke-скрипт «сервис отвечает 200 на `/healthz`».
9. CI: формат, линт, тесты бекенда и фронтенда, сборка.
10. `.gitignore` для артефактов Rust/Node/SQLite.

Definition of Done:

- `cargo run -p open_kanban_service` поднимает сервис, `/healthz` → `200`;
  БД создаётся в указанном через env файле, миграции применяются.
- `npm ci && npm run build` во фронтенде проходит.
- `cargo fmt --check`, `cargo clippy -- -D warnings`, `cargo test`, `biome ci`,
  `vitest run` — зелёные локально и в CI.
- README позволяет новому человеку запустить проект без чтения кода.

## Итерация 1 — MVP Kanban

**Цель:** сквозной сценарий из [goals_ru.md](goals_ru.md#8-критерии-приёмки-итерации-1).

Порядок срезов (каждый срез — работающий вертикальный слой):

| Срез | Бекенд | Фронтенд | Проверка |
|---|---|---|---|
| S1. Аутентификация | регистрация, вход, refresh, выход, middleware проверки access-токена | формы регистрации/входа, хранение access в памяти, авто-refresh | API-тесты + ручной вход |
| S2. Пространства и роли | CRUD пространства, участники, назначение админов, матрица прав | список пространств, настройки, участники | негативные тесты прав |
| S3. Доски и колонки | CRUD досок, колонок, порядок | экран доски, колонки, добавление/переименование | reload сохраняет порядок |
| S4. Задачи | CRUD задач, версии, архив | карточки задач, редактор, оптимистичные мутации | тесты конфликта `409` |
| S5. Перемещение | move внутри доски и между досками (транзакция + пересчёт позиций) | drag & drop, откат при ошибке, индикация конфликта | сценарий приёмки п.4–5, п.8 |
| S6. Полировка | OpenAPI полный, валидация, лимиты login | пустые состояния, ошибки, загрузка | e2e Playwright |

Definition of Done:

- Все критерии приёмки I1 из `goals_ru.md` выполнены.
- OpenAPI покрывает 100% публичных эндпоинтов; клиентские типы генерируются
  и компилируются.
- Матрица прав покрыта тестами (по одному негативному тесту на запрет).
- Перенос задачи между досками атомарен и покрыт тестом на сбой/конфликт.
- В логах нет паролей, токенов и хешей; `409` возвращается при конкурентном
  изменении.
- Документация обновлена: README (запуск/переменные), `doc/` соответствует
  фактическому API.

## Итерация 2 — Зрелость

- Аудит: `activity` для задач (создание, изменение, перемещение, архивация),
  лента на доске.
- Email: подтверждение адреса и восстановление пароля (SMTP через `lettre`),
  приглашения со статусом `invited` и принятием.
- Архивация/восстановление пространств, досок, колонок и задач.
- Списки: пагинация, фильтры (по колонке, автору, архивным), поиск по
  заголовку.
- Rate limit и базовая защита от перебора на всех auth-эндпоинтах.
- Бэкап/восстановление: документированная процедура + скрипт в `tools/`.
- Поставка: multi-stage `Dockerfile`, инструкция деплоя, том для файла БД.
- Изменения схемы (при необходимости) — отдельными миграциями.

DoD: сценарий «админ восстанавливает удалённую задачу из архива», «пользователь
подтверждает email и сбрасывает пароль», «лента событий доски показывает
перенос задачи между досками».

## Итерация 3 — Рост

- Realtime-обновления доски (WebSocket или SSE) с разрешением конфликтов.
- Приватные доски и тонкие права на уровне доски.
- Копирование/перенос задачи между пространствами (если Q4 будет решён
  положительно).
- Короткие ключи задач, WIP-лимиты колонок, шаблоны досок.
- Комментарии/вложения — только после решения о хранении файлов (локальный
  диск против S3-совместимого хранилища).
- Локализация EN, словари строк.

## Итерация 4 — Масштаб (при необходимости)

- Оценка перехода на PostgreSQL: выделение слоя репозиториев, миграции,
  тесты на обоих драйверах.
- Несколько экземпляров сервиса, health-check за прокси.
- Импорт/экспорт (JSON), интеграции (webhooks).
- SSO/OAuth — только при появлении реального запроса.

## Что не делаем до I3

- Микросервисы, брокеры, кеши, Kubernetes.
- Собственную UI-библиотеку компонентов.
- Мобильные приложения.
- Абстракции «на будущее»: репозитории-интерфейсы там, где одна реализация,
  и обобщённые обработчики без второго потребителя.

## Отслеживание

Статусы задач итерации удобно вести в самом Open Kanban, когда MVP готов.
До этого — чек-листы в этом документе или в issues выбранной площадки;
правило одно: **задача закрыта только при наличии проверки** (тест,
демо-сценарий или документированная команда).
